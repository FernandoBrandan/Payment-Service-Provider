# `CreateApiClientUseCase`

## Decisiones antes del código

Antes de escribirlo, hay que cerrar 4 decisiones que afectan el diseño:

| Decisión
| Elección para portfolio
| Por qué

- ¿Quién puede crear un `ApiClient`?
- - **Merchant dueño** (self-service) o **Admin** (manual)
- - El merchant se registra, completa KYC, y cuando quiere integrarse crea su client. Admin puede hacerlo por back-office.

- ¿Relación 1:1 o 1:N con merchant?
- - **1:1** con unique constraint en DB
- - En portfolio sobra complejidad. Si mañana querés N (app móvil, etc.), se quita el unique y no rompe nada más.

- ¿Auto-create al aprobar merchant, o lazy al pedir primera key?
- - **Ambos**: auto-create en `approve()` (happy path), use case expuesto para backfill y admin
- - Te cubre el caso de merchants existentes sin client + el onboarding nuevo.

- ¿Idempotente?
- - **Sí**: si ya existe, devuelve el existente con `created: false`
- - Evita 409 por doble-click o reintentos. El caller decide qué hacer con el flag.

---

**Impacto downstream**: `IssueApiCredentialUseCase` deja de hacer "get or create".
Ahora **requiere** que el `ApiClient` exista.
El controller (o un `OnboardingUseCase` que orqueste) hace `create` → `issue`.
Esto separa responsabilidades y evita que un endpoint de "emitir key" tenga side effects de crear clientes.
